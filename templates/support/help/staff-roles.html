Invite people from Staff. They get an SMS link and choose a password.

  • A role decides what someone can do: Owner, Manager, Accountant, Caretaker, Leasing agent, Maintenance or Viewer. Copy a role to make your own on Roles.
  • You can limit a person to some properties, or to branches: they then see every property in those branches, including ones added later. Set up branches on Branches and choose each property's branch on its edit page.
  • Viewers can only look, and do not count against your plan's team members.
  • Everyone can turn on two-step login on their security page.

API keys

An API key lets another program, such as your accounting software, read your data. The owner makes keys on Staff → API keys, choosing what each key may read: properties and units, tenants, leases, invoices or payments. Under "May change" a key can also be allowed to record payments, or to add and update tenants; leave it empty for a key that only reads.

  • The key is shown once. Keep it like a password; if it leaks, revoke it and make a new one.
  • A key reads with the rights of the person who made it, and stops working if they leave or stop being able to manage the organization. Up to 10 keys can be in use at a time.
  • Send Authorization: Bearer <key> with a GET to /api/v1/me/, /api/v1/properties/, units, tenants, leases, invoices or payments.
  • Lists come in pages: add ?limit= (up to 200) and pass back next_cursor as ?cursor=. Add ?updated_since=2026-10-01 to fetch only what changed. Money is sent as text, such as "15000.00".
  • Tenants' ID numbers, KRA PINs, emergency contacts and notes are never sent. Each key may make 120 requests a minute.
  • Add /<id>/ to read one item, such as /api/v1/tenants/<id>/.
  • To record a payment, POST JSON to /api/v1/payments/ with lease_id, amount, method (MPESA, CASH, BANK, CHEQUE or OTHER) and, if you like, paid_at, reference and tenant_id. Send an Idempotency-Key header that is different for each payment: if the same request is sent again within a day, the first answer comes back and nothing is recorded twice. The payment is confirmed and receipted as if the key's maker had entered it.
  • To add a tenant, POST name and phone (and, if you like, kind, contact_person, alt_phone, email, language) to /api/v1/tenants/; to change one, PATCH those fields to /api/v1/tenants/<id>/. ID numbers, KRA PINs, emergency contacts and notes cannot be written through the API.
  • Changes made through the API appear in the activity log in the maker's name, with the key that made them. A lapsed (read-only) account can still read but not write.

Webhooks

A webhook tells another program when something changes, so it does not have to keep asking the API. The owner adds one on Staff → Webhooks, giving an https:// address on that program's server and the events to send: payment confirmed or reversed, invoice issued or voided, lease activated or ended, tenant added or updated.

  • Events go out within about five minutes, as a POST of JSON: {"id", "type", "created_at", "data": {"object": {...}}}. The object looks the same as in the API.
  • Each webhook has a signing secret, shown once. Every event carries X-LPMS-Signature: t=<time>,v1=<signature>, where the signature is the HMAC-SHA256 of <time>.<body> with the secret, in hex. Check it, refuse times more than 5 minutes old, and ignore an X-LPMS-Delivery you have already seen: the same event can arrive twice.
  • Answer with a 2xx within 10 seconds. Otherwise we try again after 1 minute, 5 minutes, 30 minutes, 2 hours, 6 hours and 12 hours. After 25 failures in a row the webhook is paused; events are kept for 30 days and sent when you resume it. A failed event can be sent again by hand.
  • A webhook sends with the rights of the person who added it and waits if they leave. Only events after it was added are sent. Addresses on private networks are refused. Up to 5 webhooks per organization.
